## 组合模式

不用组合模式情况下，功能的实现要在一个类中的方法里实现，如果功能复杂的话，要拆分成几个方法，在使用组合模式的情况下，可以把一个功能拆分成几个节点，按照执行顺序，每个节点内部都有一个属性，指向下一个节点，比如说第一个节点用来从数据库查询数据，查询结果保存到中间变量，调用第二个节点，执行功能逻辑，第三个节点把结果返回
优点的话就是逻辑清晰，扩展性强，比如说在这个例子中，功能有变化，我只需要修改第二个节点就可以了

## 小红书

### 介绍

我做这个论坛项目的目的主要是为了熟悉微服务以及各种中间件，以及增强我的代码能力，接下来介绍一下项目的框架以及具体细节

这个项目共有 11 个微服务和 1 个平台基础设施

平台基础设施主要包括 4 个组件

第一个是常量和一些常用方法，比如说异常的定义，请求和返回的格式是什么
第二个是全局上下文，主要是通过 Java 的 ThreadLoacl 、servlet 的过滤器，Feign 的拦截器实现请求全局用户 id 唯一
第三个是记录请求日志，主要是通过切面记录请求的日志
第四个是全局统一序列化以及反序列

接下来是微服务部分，我把它分为 4 个层次

最底层是基础服务部分，共有 3 个
第一个是对象存储服务，我使用策略模式实现阿里云和 Minio 两种存储
第二个是分布式 id 服务，使用了美团开源的 leaf，提供了两种生成 id 的方式，第一种号段式，主要思想是先从数据库申请一批 id，等即将耗尽了再去申请，第二种是雪花 id，一个 id 共分为三个部分，第一个部分是机器号，第二个部分是时间戳，第三个部分是同一个时间戳的第几个 id
第三个是键值对存储服务，主要使用卡桑德拉分布式数据库存储评论的内容以及帖子的内容

往上一层是用户服务
它主要的作用是为其它服务提供接口，比如向登录服务提供注册接口，向笔记服务提供查询用户信息的接口

再往上一层是用户频繁接触的服务
第一个是登录服务，主要提供注册和登录服务，并根据 RBAC 为用户设置权限
第二个是用户关系服务，主要提供了关注和查询关注列表，考虑到查询关注列表有高并发的可能，我又加了一层 redis 缓存
第三个是笔记服务，主要提供发布，修改，删除笔记的功能，为了模拟主从库环境，在修改笔记的功能种，我使用了延迟双删的策略，主要保证缓存与数据库的一致
第四个是评论服务，主要提供发布、查询评论的功能，其中发布评论比较复杂，涉及 5 个消费者，主要是为了统计评论的数量，评论热度的计算等等
等五个是搜索服务，主要使用 es 作为搜索引擎
第六个服务是计数服务，它比较特殊，它主要消息用户行为的 MQ 消息进行计数，比如笔记的数量，用户关注数等等

最上层是网关服务
它主要的作用是判断用户的权限，限流，分发请求

==网关（Gateway）在项目中负责哪些核心功能？比如路由转发、权限校验、限流熔断的具体实现逻辑是什么？如何针对不同业务服务（如评论、笔记）配置差异化的路由规则和限流策略？==

路由转发主要依赖于 Nacos，用户发起请求的 url 会有一个前缀，比如说请求用户服务，就会有一个 user 前缀，网关就会根据这个前缀，先请求 Nacos 找到对应的 ip 地址，然后再转发

权限校验当用户登录时会将自己拥有的权限缓存在 redis 中，之后网关会根据请求地址的不同进行鉴权

限流熔断主要根据过滤器进行 ip 限流

 ==评论发布采用 RocketMQ 异步解耦 + 批量消费实现批量插入，能否说明：==
- ==若批量插入数据库时部分数据失败（如某条评论字段非法），如何处理 “部分成功、部分失败” 的场景？==

1. **粒度拆分**：批量拉取、单条处理、单条事务，避免 “一损俱损”；
2. **异常分类**：可重试异常（重试）、不可重试异常（兜底），减少无效重试；
3. **幂等保障**：数据库唯一键 + Redis 标记，避免重复处理；
4. **兜底补偿**：死信表 + 定时任务，确保消息不丢失；
5. **MQ 优化**：小批次拉取 + 重试次数上限 + 死信 MQ，完善 MQ 层保障。

 ==项目提到 “Spring Retry + 兜底写库方案保障消息最终一致性”，请详细说明：==

 ==项目构建了 “Caffeine + Redis 二级缓存” 优化查询性能：==
- ==两级缓存的协同逻辑是什么？比如笔记查询时，优先查 Caffeine 还是 Redis？缓存命中 / 未命中的处理流程？==

优先查本地缓存然后是 Redis 缓存，最后是数据库

```plaintext
1. 收到更新请求：
   a. 删除当前实例的本地缓存（第一次删本地）
   b. 删除 Redis 缓存（第一次删 Redis）

2. 执行数据库更新操作

3. 发布“缓存失效事件”到消息队列（通知其他实例删本地缓存）

4. 延迟 T 时间后：
   a. 再次删除当前实例的本地缓存（第二次删本地）
   b. 再次删除 Redis 缓存（第二次删 Redis）

5. 兜底机制：本地缓存和 Redis 均设置合理的过期时间
```

本地缓存我设置的是 1 分钟，Redis 的过期时间我采用的是随机分布，但不超过 3 分钟，出现本地缓存（Caffeine）与 Redis 数据不一致主要就是笔记更新

## MyDB

### 介绍

**tm - 事务模块**

主要提供了事务的开启、提交、撤销和状态查询功能，它主要靠操作事务文件来实现这些功能，比如说查询一个事务 id 为 3 的事务，内部有一个方法通过 id 计算事务在文件的偏移，然后读取文件，如果为 0 则表示事务还在进行，如果为 1 表示事务已提交，如果为 2 表示事务已撤销

**dm - 数据管理模块**

这个模块主要有三个作用，分别是读写文件，通过日志保障持久性

第一个是读数据主要根据数据的 64 位 id，id 的前 32 位是数据页的位置，后 32 位是数据在数据页的偏移

第二个是写数据，主要先获取有足够空闲空间的数据页，然后先写入日志，再插入数据

而且在读写过程中，利用引用计数实现了一个简易的缓存框架

最后是日志保障持久性，在系统启动时会遍历两次日志
第一次会正序扫描事务的所有日志，主要针对以提交的事务
1. 如果日志是插入操作 (Ti, I, A, x)，就将 x 重新插入 A 位置
2. 如果日志是更新操作 (Ti, U, A, oldx, newx)，就将 A 位置的值设置为 newx
第二次会倒序扫描事务的所有日志，主要针对非提交的事务
3. 如果日志是插入操作 (Ti, I, A, x)，就将 A 位置的数据删除
4. 如果日志是更新操作 (Ti, U, A, oldx, newx)，就将 A 位置的值设置为 oldx


**vm - 版本管理模块**

这个模块定义了记录的格式，以及实现了MVCC，串行化，以及死锁检测
记录主要分为 3 个部分，第一个部分是创建该记录的事务 id，第二个是删除该记录时的事务 id，第三个部分是记录的数据

死锁检测主要依赖有系统内部有两个散列表，
第一个散列表是数据 UID 被某个事务 XID 持有
第二个散列表是正在等待数据 UID 的事务 XID 列表
每次加锁是会使用深度优先遍历，看有没有成环，如果有说明死锁了，直接报错，撤销事务


**tbm - 表管理模块**

这个模块就是表管理，表头会有指向下一个表的数据 uid

**im - 索引管理模块**

这个模块使用的是 B+ 树索引
