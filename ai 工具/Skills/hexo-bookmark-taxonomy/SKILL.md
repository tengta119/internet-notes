# Hexo 博客文章分类与标签整理 Skill

## 适用场景

当用户要求整理、规范、重构 Hexo 博客文章的：

- `categories`
- `tags`
- 分类体系
- 标签体系
- 文章知识结构

时使用本 Skill。

默认目标项目路径：

```text
D:\data\myblog
```

默认文章目录：

```text
D:\data\myblog\source\_posts
```

如果用户明确提供了其他 Hexo 项目路径，则以用户提供的路径为准。

---

## 核心目标

不要把任务理解成“给每篇文章随便加几个标签”。

本 Skill 的真正目标是：

> 从整个博客的内容出发，建立一套统一、清晰、可扩展、适合长期维护的文章分类与标签体系，并将现有文章规范化到该体系中。

必须同时考虑“单篇文章是否合理”和“整个博客是否一致”。

---

# 工作原则

## 1. 内容优先

分类和标签必须主要根据文章实际内容判断，而不是仅根据：

- 文件名
- 标题
- 已有标签
- 目录名称

标题和已有 metadata 可以作为辅助信息，但不能替代正文分析。

## 2. 全局一致优先于局部最优

同一技术、概念或主题在不同文章中必须尽可能使用相同的规范名称。

例如：

```text
SpringBoot
Spring Boot
springboot
Springboot
```

应统一成一个规范名称，例如：

```text
Spring Boot
```

同理：

```text
Java开发
Java 后端
Java开发技术
```

如果它们实际表达同一层次的主题，应合并为统一分类或统一标签。

## 3. Categories 与 Tags 职责不同

### Categories

用于表达文章所属的主要知识领域或主题类别。

特点：

- 数量较少
- 稳定
- 粒度较粗
- 适合构建博客导航
- 同类文章应尽量复用已有分类

### Tags

用于表达文章涉及的具体技术、工具、概念、方法或细分主题。

特点：

- 粒度更细
- 数量可以适当增加
- 可以描述文章具体涉及的技术点
- 仍然必须保持命名统一

一般情况下，不要把过于具体的技术版本号、偶然出现的关键词直接当成高价值标签。

## 4. 避免分类爆炸

不要为了让每篇文章“看起来分类完整”而创建大量只有 1 篇文章使用的分类。

当多个分类语义高度接近时，优先考虑合并。

## 5. 不过度标签化

标签应具有检索或聚合价值。

不要把文章正文中出现过的普通词汇全部变成 tags。

例如，一篇 Java 文章出现“代码、对象、方法、变量”等普通词汇，不代表这些都应该成为标签。

## 6. 保持正文完全不变

原则上只允许修改 Markdown Front Matter 中的：

```yaml
categories:
tags:
```

禁止修改：

- 标题
- 正文
- 代码块
- 图片链接
- 图片路径
- 超链接
- 引用
- HTML
- 数学公式
- 文件名
- 文件目录结构

除非用户明确要求修改其他内容。

# 标准执行流程

## Phase 0：确认项目

首先确认：

1. 项目路径存在。
2. 项目看起来是 Hexo 博客。
3. `source/_posts` 存在。
4. 存在可解析的 Markdown 文章。

如果路径无法访问，不要凭空假设文章内容。

---

## Phase 1：扫描文章

递归扫描 `_posts` 下所有 Markdown 文件。

至少收集以下信息：

```text
文件路径
文章标题
已有 categories
已有 tags
正文内容
```

如果文章 Front Matter 不规范，也需要记录问题，但不要擅自修改与本任务无关的字段。

---

## Phase 2：分析现有体系

统计：

### Categories

- 分类名称
- 每个分类对应文章数量
- 近义分类
- 大小写不一致
- 中英文命名不一致
- 过细分类
- 明显错误分类

### Tags

- 标签名称
- 使用次数
- 同义标签
- 大小写差异
- 拼写差异
- 中英文差异
- 可以合并的标签
- 低价值标签

输出一个全局视角的现状分析。

---

## Phase 3：建立规范体系

在修改任何文章之前，先设计统一的 taxonomy。

建议输出两个表。

### Categories 规范表

| 原分类 | 规范分类 | 操作 | 原因 |
|---|---|---|---|
| Java开发 | 后端开发 | 合并 | 与其他后端技术文章保持一致 |

### Tags 规范表

| 原标签 | 规范标签 | 操作 | 原因 |
|---|---|---|---|
| SpringBoot | Spring Boot | 重命名 | 命名统一 |

如果某个分类或标签不需要修改，也不必强行调整。

---

# Categories 设计规则

优先建立“稳定的知识领域”，而不是按照每项技术建立大量一级分类。

可以参考：

```text
编程语言
后端开发
数据库
中间件
计算机基础
算法
人工智能
工具
项目实践
学习笔记
```

但以上仅为示例，不能机械套用。

必须结合博客真实内容决定最终体系。

### 一级分类的判断标准

一个主题适合作为 category，通常满足至少一项：

- 能覆盖多篇文章
- 是长期稳定的知识领域
- 用户未来很可能继续写该主题
- 能作为博客导航入口

一个只描述单篇文章具体技术点的词，通常更适合作为 tag。

---

# Tags 设计规则

标签优先表达：

- 编程语言
- 框架
- 数据库
- 中间件
- 开发工具
- AI 工具
- 编程概念
- 协议
- 架构模式
- 具体技术主题

例如：

```text
Java
Spring Boot
MySQL
Redis
RocketMQ
Docker
JVM
并发编程
分布式系统
```

但最终名称必须根据整个博客现有内容统一决定。

---

# 分类与标签判定规则

对于每篇文章，按以下优先级判断：

1. 文章核心主题是什么？
2. 它属于哪个稳定知识领域？
3. 文章具体涉及哪些技术或概念？
4. 这些技术是否具有独立检索价值？
5. 与其他文章中的命名是否一致？
6. 是否存在更合适的已有分类或标签？

最终形成：

```yaml
categories:
  - xxx

tags:
  - xxx
  - xxx
```

除非博客本身采用多级分类，否则优先使用简单、稳定的一级 categories。

# 修改策略

## 修改前必须完成

在真正写入文件前，生成一个“变更计划”。

至少包括：

```text
文章数量
当前分类数量
当前标签数量
规范后分类数量
规范后标签数量
分类合并/重命名
标签合并/重命名
```

同时给出若干典型文章的调整示例。

如果当前运行环境允许安全地查看 Git 状态，应先检查工作区是否存在用户未提交修改。

### Git 工作区有未提交修改时

不要覆盖明显属于用户的现有改动。

修改前应尽可能：

- 保留原始状态
- 缩小修改范围
- 通过 diff 验证只修改了允许的字段

---

# 文件修改规则

对于每篇文章：

1. 解析 Front Matter。
2. 仅更新 `categories` 和 `tags`。
3. 保留其他 Front Matter 字段原样。
4. 保留正文原样。
5. 尽可能保留原有 YAML 风格和缩进。

例如原文件：

```yaml
---
title: Redis 原理
categories:
  - Java
  - Redis
 tags:
  - redis
  - Redis
---
```

整理后：

```yaml
---
title: Redis 原理
categories:
  - 后端开发
tags:
  - Redis
---
```

不得因为格式整理而顺带修改 title、date、permalink、cover 等其他字段。

# 安全约束

## 禁止事项

未经用户明确要求，不得：

- 删除文章
- 重命名文章
- 移动文章
- 修改正文
- 修改图片
- 修改链接
- 修改 Hexo 配置
- 修改主题
- 修改 `_config.yml`
- 修改非分类/标签 metadata
- 安装不必要的软件包
- 执行会破坏项目的命令

## 删除标签

只有当标签明确属于：

- 重复标签
- 同义标签
- 明显错误标签
- 无意义标签

时才可以删除。

对于存在争议的标签，应保守处理。

---

# 验收规则

修改完成后必须重新扫描文章，并执行以下检查。

## 1. Front Matter 检查

确保所有修改后的 Markdown 仍然可以正常解析。

## 2. 正文完整性检查

验证 `categories/tags` 以外的正文没有发生变化。

理想情况下，应使用 diff 或等价机制检查修改范围。

## 3. 分类一致性

检查是否仍存在：

```text
Java开发
Java 后端
Java开发技术
```

等明显的同义分类。

## 4. 标签一致性

检查是否仍存在：

```text
SpringBoot
springboot
Springboot
Spring Boot
```

等明显重复标签。

## 5. 过度分类检查

确认没有因为整理而出现大量低价值分类。

## 6. 异常文章检查

列出：

- 无法解析 Front Matter 的文章
- 无法可靠判断分类的文章
- 存在明显内容歧义的文章

这些文章宁可保守处理，也不要强行分类。

# 推荐 Agent 工作模式

当用户直接说：

> 整理我的 Hexo 博客分类和标签

应自动执行：

```text
扫描 → 全局分析 → 建立 taxonomy → 生成变更计划 → 修改 → diff 验证 → 输出报告
```

而不是：

```text
逐篇阅读 → 看到什么加什么 → 直接覆盖文件
```

前者是全局知识体系整理，后者容易导致分类和标签越来越混乱。

# 默认任务指令

当用户没有提供更具体要求时，将以下内容视为默认任务：

> 分析 Hexo 项目 `D:\data\myblog\source\_posts` 下的全部 Markdown 文章，从全局角度重新设计 categories 和 tags 体系。根据文章实际内容判断归属，统一同义分类和标签，避免分类爆炸和过度标签化。除 Front Matter 中的 `categories` 和 `tags` 外，不修改任何文章内容或其他 metadata。修改前先生成 taxonomy 和变更计划，修改后使用 diff/等价方式验证正文及其他字段未被修改，并输出完整整理报告。
