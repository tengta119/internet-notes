### **8\. JVM 类加载机制与双亲委派模型**

类加载过程：  
一个类从 .class 文件到被 JVM 加载并使用，主要经历以下三个大阶段：

1. **加载 (Loading)**：  
   * 通过“类的全限定名”获取定义此类的二进制字节流（可以从 .class 文件、ZIP 包、网络、动态生成等）。  
   * 将这个字节流所代表的静态存储结构转化为方法区的运行时数据结构。  
   * 在内存中（具体是在堆中）生成一个代表这个类的 java.lang.Class 对象，作为方法区这个类的各种数据的访问入口。  
2. **链接 (Linking)**：  
   * **验证 (Verification)**：确保 .class 文件的字节流中包含的信息符合当前虚拟机的要求，并且不会危害虚拟机自身的安全（例如，文件格式、元数据、字节码、符号引用验证）。  
   * **准备 (Preparation)**：为类的**静态变量**（static 变量）分配内存，并设置该类变量的**默认初始值**（例如 int 为 0, boolean 为 false, 引用类型为 null）。注意，此时还未执行任何 Java 代码，static final 常量（如果值是编译期确定的）会在此阶段直接赋值。  
   * **解析 (Resolution)**：将常量池内的**符号引用**（Symbolic References）替换为**直接引用**（Direct References）的过程。例如，将一个指向其他类的方法的符号名，转变为指向该方法在内存中具体地址的指针。  
3. **初始化 (Initialization)**：  
   * 这是类加载的最后一步。到了这个阶段，JVM 才真正开始**执行类中定义的 Java 程序代码**。  
   * 具体来说，就是执行类的构造器 \<clinit\>() 方法。这个方法是由编译器自动收集类中的所有**静态变量的赋值动作**和**静态语句块**（static {} 块）中的语句合并产生的。  
   * \<clinit\>() 方法的执行顺序是按照语句在源文件中出现的顺序决定的。  
   * JVM 会保证在子类的 \<clinit\>() 方法执行前，父类的 \<clinit\>() 方法已经执行完毕。

**双亲委派模型 (Parent-Delegation Model)：**

* **工作流程**：当一个类加载器（ClassLoader）收到类加载请求时，它**不会**首先自己去尝试加载这个类，而是把这个请求**委派给它的父类加载器**去完成。这个过程会一直递归向上，直到委派到最顶层的**启动类加载器**（Bootstrap ClassLoader）。  
* 只有当父加载器在它的搜索范围内**找不到**所需的类，并反馈无法完成加载时，子加载器才会**自己**尝试去加载这个类。  
* **设计目的**：  
  1. **避免类的重复加载**：通过这种委派机制，一个类（例如 java.lang.Object）无论被哪个加载器请求加载，最终都会被顶层的启动类加载器加载，确保了在程序中任何地方获取到的 java.lang.Object 都是同一个 Class 对象。  
  2. **保证安全（沙箱机制）**：这是最核心的目的。它防止了 Java 核心 API 被恶意篡改。例如，如果有人恶意编写一个 java.lang.String 类，并试图用它来替换 JDK 自带的 String。在双亲委派模型下，加载 java.lang.String 的请求最终会委派给顶层的启动类加载器，它会加载 JDK 核心库中的 rt.jar 里的 String 类，而不是用户自定义的那个，从而保护了 Java 程序的安全和稳定。

### **9\. Spring 核心：IOC、Bean 生命周期与 AOP**

**IOC 容器的理解：**

* IOC（Inversion of Control，控制反转）是 Spring 的核心思想。在传统编程中，我们 new 一个对象，是“主动”控制对象的创建；而在 Spring 中，对象的创建、依赖关系的注入和生命周期的管理，都交给了 Spring 容器来“被动”控制，这就是“反转”。  
* ApplicationContext（应用上下文）就是这个 IOC 容器的最终体现。它是一个超级工厂，负责**实例化、配置和组装** Bean。  
* 在 SpringBoot 启动时（执行 SpringApplication.run()），它会自动创建一个 ApplicationContext（例如 AnnotationConfigApplicationContext）。这个上下文会去扫描启动类所在的包及其子包（通过 @ComponentScan），找到所有被 @Component、@Service、@Repository、@Controller 等注解标记的类，将它们注册为 Bean 定义（BeanDefinition），然后按照这些定义去创建和管理 Bean 实例，并处理它们之间的依赖（@Autowired）。

Bean 的生命周期（简化版）：  
一个 Bean 在 Spring 容器中的旅程大致如下：

1. **实例化 (Instantiation)**：Spring 容器通过 BeanDefinition，使用反射（Class.forName）创建 Bean 的实例。  
2. **填充属性 (Populate Properties)**：Spring 按照 Bean 定义中的依赖关系（如 @Autowired），将其他 Bean 注入到当前 Bean 的属性中。  
3. **Aware 接口回调**：如果 Bean 实现了 BeanNameAware、BeanFactoryAware 等接口，Spring 会调用这些接口的方法，让 Bean “感知”到自己的名字和所在的工厂。  
4. **BeanPostProcessor (前置处理)**：执行 BeanPostProcessor 的 postProcessBeforeInitialization 方法。**AOP（面向切面编程）的代理对象创建，通常就是在这个阶段完成的。**  
5. **初始化 (Initialization)**：  
   * 如果 Bean 实现了 InitializingBean 接口，调用其 afterPropertiesSet() 方法。  
   * 如果 Bean 定义了 init-method，调用该指定的方法。  
6. **BeanPostProcessor (后置处理)**：执行 BeanPostProcessor 的 postProcessAfterInitialization 方法（AOP 代理也可能在此处完成）。  
7. **Bean 可用**：此时，Bean 已经完全初始化，驻留在容器中，可以被业务逻辑使用了。  
8. **销毁 (Destruction)**：当容器关闭时（如 SpringBoot 应用停止）：  
   * 如果 Bean 实现了 DisposableBean 接口，调用其 destroy() 方法。  
   * 如果 Bean 定义了 destroy-method，调用该指定的方法。

AOP 在项目中的应用：  
AOP（切面编程）在我的“仿小红书”项目中应用非常广泛，它允许我们将“横切关注点”（如日志、权限）从主业务逻辑中解耦出来：

* **事务管理**：最典型的应用。我们使用 @Transactional 注解来声明事务。Spring AOP 会创建一个代理对象，在**目标方法执行前**（@Before）开启事务，在**方法执行后**（@AfterReturning）提交事务，在**抛出异常时**（@AfterThrowing）回滚事务。  
* **全局日志记录**：我编写了一个自定义的日志切面（@Aspect），使用 @Around 或 @Before 通知，来切入所有 Controller 层的方法。它可以自动记录每个 HTTP 请求的入参、出参、执行耗时、以及操作的用户 ID，这对于调试和审计非常关键。  
* **权限校验**：我也使用 AOP 实现了权限校验。例如，某些接口（如“删除笔记”）需要特定的权限。我创建了一个自定义注解（如 @CheckPermission），并编写一个切面。在方法执行前，切面会检查当前登录用户的角色，如果不符合注解要求的权限，就直接抛出异常，阻止方法继续执行，而业务代码本身不需要写 if-else 判断。

### **10\. 项目优化：ZSet \-\> RoaringBitmap**

切换原因：  
在点赞功能中，我们有两个核心需求：1. 判断某用户是否点赞； 2\. 统计总点赞数。

* **ZSet 方案**：我们最初使用 ZSet，Key 是笔记 ID，Value 是用户 ID，Score 是点赞时间戳。这可以实现需求 1 和 2（ZCard 统计总数）。  
* **痛点**：当一篇笔记成为爆款，有**几百万**用户点赞时，ZSet 的内存开销变得巨大。ZSet 内部使用 dict \+ skiplist 存储，每个 member（用户 ID）都是一个独立的 redisObject，并且 skiplist 和 dict 本身也有指针开销。这导致 Redis 内存被快速消耗。

RoaringBitmap (咆哮位图) 的原理：  
RoaringBitmap 是一种高度压缩的位图数据结构，它在性能和内存效率上取得了极佳的平衡，尤其适合存储稀疏或密集的整数集合。  
它的核心思想是**分块**：

1. 它将 32 位的整数空间（0 到 2\<sup\>32\</sup\>-1）划分为 2\<sup\>16\</sup\>（65,536）个**块（Chunk）**，每个块可以存储 2\<sup\>16\</sup\> 个连续的数字（例如，块 0 存储 0-65535，块 1 存储 65536-131071...）。  
2. 对于每个块，它会智能地选择两种存储容器：  
   * **ArrayContainer（数组容器）**：当这个块中的整数**稀疏**时（即个数 ≤ 4096），它会使用一个**有序数组**来存储这些整数。内存开销极小。  
   * **BitmapContainer（位图容器）**：当这个块中的整数**密集**时（即个数 \> 4096），它会使用一个标准的\*\*位图（Bitmap）\*\*来存储，固定占用 8KB 内存（2\<sup\>16\</sup\> bit）。  
3. RoaringBitmap 本质上是一个存储这些容器的顶层索引。

**优势：**

* **对比 BitMap**：标准的 BitMap 在处理**稀疏**数据时是灾难性的。如果我只想存储用户 ID 1 和 1,000,000,000，BitMap 需要分配 10 亿 bit (约 120MB) 的内存。而 RoaringBitmap 只会创建两个 ArrayContainer，内存占用几乎为 0。  
* **对比 ZSet**：在我们的点赞场景，用户 ID 是密集且庞大的。RoaringBitmap 会将它们压缩存储在 BitmapContainer 和 ArrayContainer 中，内存占用率远低于 ZSet（通常可以压缩 10 倍甚至更多）。

因此，切换到 RoaringBitmap（通过 RedisRoaring 这样的 Redis Module 或在客户端实现）后，我们极大地降低了 Redis 的内存使用，同时 isLiked(userId)（contains 操作）和 getLikeCount()（cardinality 操作）的性能依然非常高。

### **11\. 微服务组件：Nacos & Gateway**

Nacos (注册与心跳)：  
Nacos 在我的架构中同时扮演“注册中心”和“配置中心”的角色。

* **服务注册**：当一个 Spring Cloud 微服务（例如“用户服务”）启动时，spring-cloud-starter-alibaba-nacos-discovery 客户端会自动将该服务的元数据（包括服务名 spring.application.name、IP 地址、端口号等）通过 HTTP/Rest 接口**注册**到 Nacos Server。  
* **心跳机制**：注册成功后，Nacos 客户端会启动一个**定时任务**，默认**每 5 秒**向 Nacos Server 发送一个**心跳包**（UDP 或 HTTP，新版主要是 HTTP）。  
* **健康维护**：  
  * Nacos Server 通过监控这些心跳来判断实例的健康状态。  
  * 如果 Server 在 **15 秒**内没有收到某个实例的心跳，它会将其标记为“**不健康**”（unhealthy）。  
  * 如果 Server 在 **30 秒**内（这个阈值可配）持续没有收到心跳，它会认为这个实例已经宕机，并将其从服务列表中**剔除**，防止其他服务调用到这个“僵尸”实例。

**Gateway (职责与全局过滤器)：**

Gateway 是我们整个微服务架构的**统一入口**，所有来自客户端（App、Web）的流量都必须先经过它。

* **核心职责**：  
  1. **动态路由**：根据请求的 URL 路径（例如 /api/user/...）将其转发到下游的“用户服务”；根据 /api/note/... 转发到“笔记服务”。它会自动从 Nacos 拉取服务列表，实现负载均衡。  
  2. **身份认证与鉴权**：作为统一入口，它是执行安全策略的最佳地点。  
  3. **限流与熔断**：可以集成 Sentinel 来保护下游服务，防止雪崩。  
  4. **跨域处理 (CORS)**：统一配置跨域。  
  5. **请求/响应日志**：统一记录全局日志。  
* 全局过滤器 (GlobalFilter)：  
  我在项目中确实自定义了 GlobalFilter，主要用于统一的身份认证：  
  1. 我实现了一个 GlobalFilter 并设置了高优先级（@Order(-1)）。  
  2. 在这个过滤器中，我定义了一个“白名单”路径（如登录、注册接口），这些路径直接放行。  
  3. 对于其他所有需要登录的请求，过滤器会从请求头（Header）中获取 Authorization 令牌（Token）。  
  4. 如果 Token 不存在，立即返回 401（未授权）错误，**短路**后续流程，不再转发到下游服务。  
  5. 如果 Token 存在，就调用“认证服务”（或本地 JWT 工具类）校验 Token 的有效性。  
  6. 校验通过后，我会将 Token 中解析出的**用户 ID**（userId），通过 exchange.getRequest().mutate().header(...) 的方式，**写入到一个新的请求头中**（例如 X-User-Id）。  
  7. 最后，Gateway 将这个“增强”后的请求转发给下游微服务。这样做的好处是，下游的**业务服务（如笔记服务）无需关心 Token 解析**，它们可以 100% 信任地从 X-User-Id 请求头中获取当前用户 ID，实现了安全和业务的解耦。

### **12\. 分布式 ID (美团 Leaf)**

为什么需要分布式 ID：  
在微服务架构下，使用 MySQL 自增 ID 会带来很多问题：

1. **数据分片（分库分表）**：这是最主要的原因。为了应对高并发，我们的“笔记表”会水平拆分到多个数据库或多个表中。如果使用自增 ID，每个分片都会产生 1, 2, 3... 这样的 ID，导致**全局 ID 冲突**。  
2. **服务解耦**：如果“用户服务”在创建用户时需要先在“认证服务”中插入一条记录，如果都依赖自增，ID 的传递会变得非常混乱。  
3. **安全性**：自增 ID 是连续的，容易被爬虫遍历，暴露业务数据量（例如，新注册用户的 ID 是 10001，昨天是 10000，说明昨天只有 1 个注册）。

因此，我们需要一个**全局唯一**、**高性能**、**高可用**且最好是**趋势递增**（有利于 B+ 树索引）的 ID 生成方案。

Leaf 模式选择：  
美团 Leaf 提供了两种模式，在我的项目中，我们选择了号段模式 (Segment Mode)。

* **号段模式 (Segment Mode) 原理**：  
  1. Leaf 需要一个单独的数据库表来存储**号段**信息，表中记录了每种业务（biz\_tag，如 user\_id, note\_id）当前的 max\_id 和 step（步长，即一次拉取的号段长度，例如 1000）。  
  2. 当“用户服务”需要一个 ID 时，它会请求 Leaf-Server。  
  3. Leaf-Server 发现内存中的 user\_id 号段已用完，它会去数据库更新 biz\_tag \= 'user\_id' 这一行：UPDATE ... SET max\_id \= max\_id \+ step。  
  4. 假设 max\_id 从 1000 变成了 2000，Leaf-Server 就获得了 \[1000, 1999\] 这个**号段**，并将其加载到内存中。  
  5. 然后，Leaf-Server 在**内存中**依次分发 1000, 1001, 1002... 给“用户服务”。  
  6. **双缓冲**：Leaf 还会做一个优化，当号段用到 10%（例如 1900）时，它会异步提前去加载下一个号段 \[2000, 2999\]，确保服务永远不会因为等待数据库而卡顿。  
* **为什么不用 Snowflake 模式**：Snowflake 模式（41 位时间戳 \+ 10 位机器 ID \+ 12 位序列号）虽然性能极高且 ID 趋势递增，但它有一个致命弱点：**强依赖系统时钟**。如果发生**时钟回拨**（例如 NTP 校时导致服务器时间倒退），它可能会生成重复的 ID，或者服务卡住直到时钟追上。在金融和核心业务场景，这种不确定性是高风险的。“号段模式”虽然依赖数据库，但 ID 是绝对可靠的，并且 Leaf-Server 的高可用部署（DB 双主、Server 集群）完全能满足我们的性能和可用性要求。

### **13\. 项目二：MyDB (日志与恢复)**

在 "MyDB" 中，我实现的核心是保障 ACID，特别是 A（原子性）和 D（持久性），这主要依赖于日志和恢复机制。我实现的是一个简化的、基于 **Write-Ahead Logging (WAL)** 策略的 **Redo/Undo Log** 系统。

核心策略 (WAL)：  
在我的设计中，严格遵守 WAL（预写日志） 原则：

* **规则**：在任何数据（Data Page）的“脏页”从内存（Buffer Pool）刷写到磁盘（DB 文件）**之前**，该数据变更所对应的**日志（Log Record）必须先被持久化到磁盘**（Log 文件）上。  
* **原因**：日志文件是顺序写的，非常快。数据文件是随机写的，很慢。如果先写数据再写日志，万一数据写成功了，日志没写成功，此时宕机，数据库就“多出”了一笔未提交的“幽灵数据”且无法回滚。WAL 保证了日志总是在数据之前，确保了可恢复性。

崩溃恢复 (Crash Recovery) 流程：  
当 "MyDB" 发生崩溃并重启时，恢复流程被触发：

1. **分析 (Analysis) 阶段**：  
   * 从头（或从上一个 Checkpoint）开始扫描**日志文件 (Log File)**。  
   * 这个过程会做两件事：  
     1. 构建一个“**活跃事务列表**”（Active Transaction Table）：记录在日志中看到了 BEGIN 但没有看到 COMMIT 或 ABORT 的所有事务。  
     2. 构建一个“**脏页表**”（Dirty Page Table）：记录被日志修改过，但在日志中没有看到对应“刷盘完成”记录的所有数据页。  
2. **重做 (Redo) 阶段**（保证持久性）：  
   * 从“脏页表”中记录的最早的日志（LSN）开始，**重新**扫描日志。  
   * **无差别地**（无论事务是否提交）将在日志中记录的所有**数据变更操作**（例如，"将 Page 10 的偏移量 50 处的值从 'A' 改为 'B'"）**重新在内存的 Buffer Pool 中执行一遍**。  
   * 这保证了所有**已提交**（Committed）事务的修改一定被恢复到了内存中（即使它们在崩溃前没来得及刷盘）。  
3. **撤销 (Undo) 阶段**（保证原子性）：  
   * 现在，我们处理在“分析”阶段找到的“**活跃事务列表**”（即崩溃时未提交的事务）。  
   * 对**每一个**未提交的事务，系统会**反向**扫描日志文件（或通过事务的 Undo 链表），找到它们所有的 Undo Log 记录。  
   * **逆序执行**这些 Undo Log（例如，"将 Page 10 偏移量 50 处的值从 'B' 改回 'A'"），将这些事务“抹掉”。  
   * 当一个事务的所有 Undo 操作都完成后，系统会为该事务写入一个 ABORT 日志。

通过 Redo-then-Undo 的流程，"MyDB" 确保了在崩溃重启后，所有已提交的事务变更都永久生效（持久性），而所有未提交的事务变更都被彻底回滚，就像它们从未发生过一样（原子性）。
