### **为什么选用 Cassandra 存储评论和笔记内容，而不是 MySQL ？**

MySQL 是关系型数据库，默认使用 InnoDB 作为存储引擎，而且在在 InnoDB 中，是使用行存储结构来存储数据的，每一行存储在数据页中，数据页的默认大小为 16 KB。当存储的文本数据很长时，InnoDB 会将部分数据存储在溢出页中，并在原数据页中保留一个指针指向溢出页。这种机制会导致更多的磁盘 I/O 操作，因为访问一条长文本数据需要读取多个数据页

其效率问题，大致可总结如下：

- **磁盘 I/O 开销**：由于 InnoDB 的行溢出机制，长文本数据需要多个页来存储和访问。这意味着读取和写入长文本数据时，需要更多的磁盘I/O操作，从而降低了性能。
- **数据页填充率**： InnoDB 的数据页大小固定为 16KB。当文本数据长度不固定时，可能会导致数据页的填充率不高，浪费存储空间，并且增加了页碎片。
- **索引效率**：对于长文本数据，InnoDB 的 B+ 树索引可能会变得低效。尤其是对 TEXT 类型列进行索引时，索引只会包含前几个字符，无法利用索引进行高效的全文检索。
- **事务开销**： InnoDB 支持 ACID 事务，事务日志和回滚日志需要额外的存储和处理。对于频繁更新的大量长文本数据，这些日志会带来显著的性能开销。

最后选用 [Cassandra](https://cassandra.apache.org/) 存储短文本，它是一种分布式 KV 存储系统，具有分布式存储、支持时间序列数据、可线性扩展的特点，适用于需要高可用性、高吞吐量和低延迟的应用场景

### 为什么使用延迟双删策略而不使用旁路缓存策略

好的，这是一个非常经典且重要的面试和实践问题。我们来深入讲解一下 Redis 中最常用的两种数据一致性策略：**旁路缓存（Cache-Aside）** 和作为其改进版的 **延迟双删（Delayed Double-Delete）**。

这两种策略的核心目标都是为了解决同一个问题：如何保证**缓存 (Redis)** 和**数据库 (DB)** 之间的数据一致性。

---

**1. 旁路缓存策略 (Cache-Aside Pattern)**

这是最经典、最常用的缓存策略，几乎所有互联网公司的开发人员都会接触到。它的核心思想是：**应用程序代码来直接维护缓存和数据库**。

**工作流程**

**读操作 (Read):**

1. 应用先从缓存（Redis）中读取数据。
    
2. 如果缓存命中（数据存在），则直接返回数据。
    
3. 如果缓存未命中（数据不存在），则从数据库（DB）中读取数据。
    
4. 将从数据库中读到的数据放入缓存中。
    
5. 向客户端返回数据。
    

写操作 (Write / Update):

这里的关键是：我们是更新缓存还是删除缓存？ 答案是 删除缓存。

1. 先更新数据库（DB）。
    
2. 再**直接删除**缓存（Redis）中对应的条目。
    

**为什么是删除缓存，而不是更新缓存？**

- **懒加载 (Lazy Loading)**：删除缓存后，只有在下次真正需要读取该数据时，才会从数据库加载并放入缓存。如果一个数据被更新后很少被读取，那么更新缓存的计算和网络开销就是一种浪费。
    
- **避免复杂性**：如果更新操作很复杂（需要计算或关联其他数据），直接删除缓存比计算后更新缓存更简单、更快速。
    
- **并发安全**：在并发写操作下，如果选择更新缓存，可能会因为写入顺序问题导致缓存中是旧数据。而删除操作相对更安全。
    

**优点 (Pros)**

1. **实现简单**：逻辑清晰，代码实现直观，易于理解和维护。
    
2. **灵活性高**：缓存的读写完全由应用层代码控制，可以方便地为不同的数据添加不同的缓存策略（如不同的过期时间 TTL）。
    
3. **数据相对一致**：在绝大多数情况下，可以保证缓存和数据库的数据一致性。读操作总是以数据库为准来填充缓存。
    

**缺点 (Cons)**

1. **首次请求延迟（冷启动问题）**：当新数据加入或缓存被删除后，第一次读取该数据的请求必然会发生缓存未命中（Cache Miss），需要查询数据库，导致这次请求的响应时间变长。
    
2. **存在短期数据不一致的风险（核心缺点）**：这是旁路缓存策略最主要的问题。考虑以下并发场景：
    
    - **线程 A (写操作)**：准备更新数据 X。
        
    - **线程 B (读操作)**：准备读取数据 X。
        
    
    **可能出现的不一致流程：**
    
    1. 线程 A 将数据库中的数据 X 更新为新值 `V2`。
        
    2. 线程 A 去删除缓存，但**因为网络延迟等原因，删除操作还没执行**。
        
    3. 此时线程 B 发起读请求，缓存命中，读到了**旧值 `V1`** 并返回。
        
    4. 线程 A 的删除缓存操作完成。
        
    
    在这个极短的时间窗口内，线程 B 读到了脏数据。不过，这种“读写并发”造成的不一致问题通常时间很短，后续的读请求会因为缓存未命中而去数据库加载新值 `V2`，系统会自动修复。**更严重的问题是“写写并发”**，下面延迟双删会详述。
    

---

**2. 延迟双删策略 (Delayed Double-Delete)**

延迟双删并不是一个独立的缓存模式，而是对**旁路缓存策略中写操作**的一种优化，旨在解决上述的并发数据不一致问题。

**问题背景：旁路缓存的致命缺陷**

考虑一个比上面更严重的并发场景（数据库主从复制延迟是常见原因）：

1. **线程 A (写)**：将数据库中 X 的值更新为 `V2`。
    
2. **线程 A (写)**：删除缓存中的 X。
    
3. **线程 B (读)**：发起读请求，发现缓存中没有 X。
    
4. **线程 B (读)**：去**从库**读取数据（因为主从延迟，读到了旧值 `V1`）。
    
5. **线程 B (读)**：将读到的旧值 `V1` 放入缓存。
    
6. **此时，缓存中的数据是旧值 `V1`，而数据库中的是新值 `V2`，数据不一致发生，并且后续的读请求都会命中这个脏数据！**
    

**工作流程**

延迟双删通过两次删除操作来解决这个问题。

**写操作 (Write / Update):**

1. **第一次删除**：在更新数据库**之前**，先删除缓存。
    
2. **更新数据库**：执行 SQL `UPDATE` 操作。
    
3. **延迟**：让当前线程**休眠一段固定的时间**（例如 500ms ~ 1s）。
    
4. **第二次删除**：再次删除缓存。
    

**为什么这样做能解决问题？**

- **第一次删除**：是为了处理“读写并发”时，在更新数据库前，有其他读请求访问缓存。这次删除可以大概率让后续的读请求穿透到数据库。
    
- **延迟+第二次删除**：这是整个策略的精髓。这个**延迟时间**的设置，是为了等待在步骤1和2之间进入的**读线程**（像上面场景中的线程B）能够完成它的“读数据库（旧值）并回填缓存”的整个过程。当休眠结束后，我们再次删除缓存，就能把那个刚被回填的脏数据给删掉。
    

**优点 (Pros)**

1. **数据一致性更高**：通过两次删除和延迟，大大降低了并发场景下缓存出现脏数据的概率，数据一致性得到显著增强。
    

**缺点 (Cons)**

1. **系统吞吐量降低**：写操作中引入了 `sleep()` 这样的同步阻塞，会占用线程资源，导致写操作的响应时间变长，系统整体的吞吐量下降。
    
2. **延迟时间难以确定**：
    
    - 延迟时间设置多长？这个时间需要大于一次“读DB+写Cache”的往返时间。
        
    - 如果设置太短，可能无法覆盖并发读操作，导致策略失效。
        
    - 如果设置太长，会过度影响性能。这个时间值非常依赖业务场景和系统环境，难以找到一个普适的完美值。
        
3. **依然存在数据不一致的可能**：这只是一个“最终一致性”的补偿方案，不是强一致性保证。如果那个并发的读请求因为各种原因（GC、网络抖动）耗时超过了你的延迟时间，那么脏数据问题依然会发生。
    
4. **增加了代码的复杂性和维护成本**：如果第二次删除失败怎么办？需要引入重试机制（比如通过消息队列异步重试），这会进一步增加系统的复杂性。
    

**总结与对比**

| 特性         | 旁路缓存策略 (Cache-Aside)  | 延迟双删策略 (Delayed Double-Delete) |
| ---------- | --------------------- | ------------------------------ |
| **实现复杂度**  | 低，逻辑清晰                | 高，需要处理延迟、失败重试等                 |
| **数据一致性**  | 相对较低，并发下有风险           | 相对较高，显著降低脏数据概率                 |
| **性能/吞吐量** | 高，写操作快                | 较低，写操作因`sleep`而变慢              |
| **适用场景**   | 对数据一致性要求不那么极致的绝大多数场景。 | 对数据一致性有较高要求，且能容忍一定性能损耗的场景。     |

**实践建议：**

- **首选旁路缓存**：对于大部分业务，数据有几百毫秒的不一致是可以接受的。旁路缓存简单、高效，是性价比最高的方案。
    
- **为缓存设置过期时间 (TTL)**：这是数据一致性的最后一道防线。即使出现了脏数据，它也能在 TTL 到期后自动失效，从而实现最终一致性。
    
- **谨慎使用延迟双删**：只有在业务对一致性有非常高的要求，且清楚地了解其性能代价时才考虑使用。
    
- **考虑更优方案**：对于金融等一致性要求极高的场景，通常会采用基于**消息队列 (MQ)** 的异步通知方案，或者使用 **Canal** 等工具订阅数据库的 `binlog` 来更新缓存，这些方案能更可靠地保证一致性，且对应用代码的侵入性更小。
