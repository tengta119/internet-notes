### **1\. Java 并发与 JMM**

**关于 synchronized 锁升级：**

synchronized 的锁升级是 JVM 为了在不同竞争情况下平衡性能开销和线程同步的一种优化手段。这个过程主要依赖对象头中的 **Mark Word**。

1. **无锁状态**：对象刚创建时，Mark Word 中锁标志位为 01，此时没有线程竞争。  
2. **偏向锁 (Biased Locking)**：  
   * **时机**：当第一个线程（T1）访问同步块时，JVM 会使用 CAS 尝试将 T1 的线程 ID 写入 Mark Word，并将锁标志位置为 01（但偏向锁位为 1）。  
   * **优点**：如果后续一直是 T1 在访问，它只需检查 Mark Word 中的线程 ID 是否是自己，无需任何 CAS 或同步操作，效率极高。  
3. **轻量级锁 (Lightweight Locking)**：  
   * **时机**：当第二个线程（T2）开始竞争时，偏向锁会撤销（膨胀）。  
   * **过程**：T1 和 T2 都会在自己的栈帧中创建一块名为“锁记录”（Lock Record）的空间，用于复制 Mark Word 的副本（Displaced Mark Word）。接着，线程会尝试使用 CAS 将对象头的 Mark Word 指向自己的锁记录地址。  
   * **成功**：CAS 成功的线程（比如 T1）获得锁，Mark Word 中的锁标志位变为 00。  
   * **失败（自旋）**：CAS 失败的线程（T2）不会立即阻塞，而是会进行“自旋”（执行空循环）等待，期待 T1 很快释放锁。  
   * **优点**：自旋避免了线程在内核态和用户态之间切换（即阻塞和唤醒）的巨大开销，适用于同步块执行时间很短的场景。  
4. **重量级锁 (Heavyweight Locking)**：  
   * **时机**：如果自旋（默认 10 次或自适应自旋）后，T2 仍然没有获取到锁，或者有更多的线程（T3, T4...）加入竞争。  
   * **过程**：锁会膨胀为重量级锁，Mark Word 的指针会指向操作系统层面的互斥量（Mutex），锁标志位变为 10。  
   * **状态**：所有未获取到锁的线程都会进入阻塞状态，交由操作系统内核来调度和唤醒。  
   * **缺点**：开销最大，但适用于同步块执行时间长、竞争激烈的场景。

**关于 volatile 与 JMM：**

* **JMM (Java 内存模型)**：JMM 是一种抽象规范，它定义了线程如何与主内存（Main Memory）以及各自的工作内存（Working Memory）交互。它规定了变量何时从主内存读取、何时刷新回主内存。  
* **volatile 的作用**：volatile 是 JMM 提供的一种轻量级同步机制。  
  1. **保证可见性 (Visibility)**：当一个线程修改了 volatile 变量，JMM 会立即使该线程的工作内存失效，并强制将新值刷新回主内存。当其他线程读取该 volatile 变量时，JMM 也会强制使其本地缓存失效，必须从主内存重新读取最新值。  
  2. **禁止指令重排序 (Ordering)**：volatile 关键字会插入“内存屏障”（Memory Barriers）。这确保了 volatile 写操作之前的所有操作，一定在它之前完成；volatile 读操作之后的所有操作，一定在它之后开始。这在“双重检查锁定（DCL）”单例模式中至关重要，可以防止因构造函数重排序导致其他线程获取到未完全初始化的对象。  
* **关系**：JMM 定义了内存交互的规则，而 volatile 是利用这些规则实现“可见性”和“有序性”的一种具体工具。它通过 JMM 提供的内存屏障机制，确保了多线程环境下对共享变量读写的特定行为。

### **2\. Redis 缓存问题**

是的，我对这三种经典缓存问题有比较深入的理解和实践：

* **缓存穿透 (Cache Penetration)**  
  * **场景**：恶意请求高并发地查询一个**数据库和缓存中都绝对不存在**的数据（例如，ID 为 \-1 的商品）。  
  * **后果**：由于缓存（Redis）每次都未命中，请求会全部“穿透”到数据库，导致数据库压力剧增甚至崩溃。  
  * **解决方案**：  
    1. **缓存空值 (Cache Nulls)**：如果数据库查询不到，我们依然在 Redis 中缓存一个空对象或特殊占位符（如 ""），并设置一个较短的过期时间（例如 1-5 分钟），防止恶意攻击。  
    2. **布隆过滤器 (Bloom Filter)**：正如我在“仿小红书”项目中使用的，可以将所有**合法**的数据（例如，所有已上架的商品 ID）提前加载到一个布隆过滤器中。当请求到来时，先过布隆过滤器：如果过滤器判断“一定不存在”，则直接拒绝请求，根本不会去查缓存和数据库。  
* **缓存击穿 (Cache Breakdown)**  
  * **场景**：某一个**热点 Key**（例如，爆款商品的详情页）在某一瞬间**突然失效**（过期了）。  
  * **后果**：在它失效的瞬间，成千上万的并发请求会同时涌入，发现缓存未命中，然后全部打到数据库上，进行重复的查询和回写，数据库瞬时压力极大。  
  * **解决方案**：  
    1. **互斥锁/分布式锁**：当缓存未命中时，只允许第一个获取到锁（例如 SETNX）的线程去查询数据库并回写缓存。其他线程则在原地等待（自旋或休眠），然后重试获取缓存。  
    2. **热点数据永不过期（逻辑过期）**：对热点数据不设置物理 TTL。而是在 Value 中存储一个“逻辑过期时间戳”。当线程发现数据“逻辑过期”时，由第一个获取锁的线程去异步开启一个新线程重建缓存，而当前线程（和其他线程）则先返回旧的（但可用的）数据。  
* **缓存雪崩 (Cache Avalanche)**  
  * **场景**：大量 Key 在**同一时间集中失效**（例如，服务重启后缓存全部清空，或者所有 Key 被设置了相同的过期时间）。  
  * **后果**：这是“击穿”的群体版。海量的请求同时穿透到数据库，导致数据库宕机，进而引发整个系统的连锁崩溃。  
  * **解决方案**：  
    1. **过期时间加随机值**：在设置缓存的过期时间时（例如 EXPIRE key time），增加一个随机偏移量（例如 EXPIRE key (time \+ random(300))）。这样可以把过期时间打散，避免集中失效。  
    2. **高可用集群**：使用 Redis Sentinel 或 Cluster 模式，确保 Redis 服务本身的高可用，避免因 Redis 宕机导致的雪崩。  
    3. **限流与熔断**：在网关层或应用层部署限流（如 Sentinel），当请求量激增时，只放行少量请求到底层，保护数据库。

### **3\. MySQL 与 MVCC**

MVCC（多版本并发控制）是 InnoDB 存储引擎在“可重复读”（RR）隔离级别下实现“读写不阻塞”的核心机制。它不依赖传统的锁，而是通过保存数据的多个历史版本来实现并发控制。

它主要依赖三个关键组件：

1. **隐藏字段**：InnoDB 会在每行数据上额外添加两个（或三个）隐藏字段：  
   * DB\_TRX\_ID：记录最后一次修改（增、删、改）这行数据的事务 ID。  
   * DB\_ROLL\_PTR：一个回滚指针，指向这条数据在 **Undo Log** 中的上一个版本。  
   * DB\_ROW\_ID：隐藏主键（如果表没有显式定义主键）。  
2. **Undo Log (回滚日志)**：当事务执行 DML（Insert, Update, Delete）时，它会将数据的“旧版本”快照存储在 Undo Log 中。这些版本通过 DB\_ROLL\_PTR 串联起来，形成一个“版本链”。  
3. **Read View (读视图)**：这是 MVCC 的精髓。当一个事务（在 RR 级别下）**首次**执行**快照读**（SELECT 语句）时，会生成一个 Read View。

Read View 是什么？  
它是一个“快照”，记录了在生成时刻，系统中所有“活跃”（即未提交）的事务 ID 列表（m\_ids），以及活跃列表中的最小 ID（min\_trx\_id）和最大 ID（max\_trx\_id）。  
工作流程 (实现可重复读)：  
当事务 A（trx\_id\_A）去读取一行数据时，它会拿着自己的 Read View（这个 Read View 在 RR 级别下只创建一次）去和这行数据的最新版本（记录在 DB\_TRX\_ID）进行比较：

1. 如果 DB\_TRX\_ID **小于** Read View 的 min\_trx\_id：说明这个版本是在事务 A 启动前就已提交的。**可见**。  
2. 如果 DB\_TRX\_ID **大于等于** Read View 的 max\_trx\_id：说明这个版本是在 Read View 生成后才开启的事务修改的。**不可见**。  
3. 如果 DB\_TRX\_ID 在 min\_trx\_id 和 max\_trx\_id 之间：  
   * 检查 DB\_TRX\_ID 是否在活跃列表 m\_ids 中：  
   * 如果**在**，说明这个版本是 Read View 生成时还未提交的（兄弟事务）修改的。**不可见**。  
   * 如果**不在**，说明这个版本是在 Read View 生成前已经提交的。**可见**。

**如果“不可见”**：事务 A 就会顺着 DB\_ROLL\_PTR 回滚指针，去 Undo Log 中查找上一个版本，然后**重复**上述的 Read View 比较规则，直到找到一个“可见”的版本为止。

由于在 RR 级别下，事务 A 始终复用**第一次**快照读时生成的 Read View，这就保证了它在整个事务期间，看到的始终是它启动时的那个数据快照，从而实现了“可重复读”。

### **4\. 项目一：仿小红书（RocketMQ 延迟双删）**

选择原因及操作流程：  
缓存一致性是分布式系统的经典难题。

* **先更新库，再删缓存**：这是最常用的方案，但如果删除缓存失败（例如 Redis 抖动或宕机），会导致数据库是新数据，而缓存是旧数据，造成不一致。  
* **先删缓存，再更新库**：在高并发下，线程 A 删了缓存，此时线程 B 来读，发现缓存没有，去读数据库（读到旧值），写回缓存。然后线程 A 才完成数据库更新。这会导致缓存中存入脏数据。

我的“延迟双删”方案就是为了解决第二种情况（脏数据）而设计的，并结合了第一种方案的思路：

1. **第一次删除**：线程 A 先删除缓存。  
2. **更新数据库**：线程 A 执行数据库的 UPDATE 操作。  
3. **发送延迟消息**：数据库更新成功后，线程 A 向 RocketMQ 发送一个**延迟消息**（例如，延迟 1-2 秒）。  
4. **第二次删除**：1-2 秒后，MQ 消费者收到消息，执行**第二次缓存删除**。

解决的问题：  
这个方案主要解决的是：在步骤 1 和步骤 2 之间，如果有其他读请求（线程 B）读了数据库的旧值并写回了缓存（脏数据），那么步骤 4 的“延迟删除”会确保这个刚被写入的脏数据最终被清除掉。这个 1-2 秒的延迟，就是为了等待那个“读旧值-写缓存”的并发操作完成。  
缺陷与兜底方案：  
您说的很对，这个方案并非完美：

1. **延迟时间**：这个“1-2秒”是一个估算值，很难精确。如果线程 B 的“读-写”操作耗时超过 2 秒，脏数据依然会存在。  
2. **第二次删除失败**：这是最大的风险。如果 MQ 消费者执行第二次删除时失败了（例如 Redis 挂了），数据还是会不一致。

为了解决这个问题，我（在简历中）提到了 **Spring Retry \+ 兜底写库 方案**：

* MQ 消费者在执行删除时，我会包裹 Spring Retry。如果删除失败（例如网络超时），它会自动重试 3 次。  
* 如果重试 3 次后仍然失败，说明 Redis 可能出现严重故障。此时，程序会捕获异常，将这条“删除失败”的消息（包含要删除的 Key）**写入一个兜底的数据库表**（或一个死信队列）。  
* 我们有单独的**定时任务**（例如XXL-Job），会定期扫描这张兜底表，不断尝试重新删除这些失败的 Key，直到成功为止，以此来保障数据的**最终一致性**。

（如果面试官追问：为什么不用 Canal 订阅 Binlog？）  
Canal 订阅 Binlog 是一种更优雅、侵入性更低的方案，它可以实现业务与缓存维护的彻底解耦。但在当时的项目选型中，考虑到我们已经重度依赖 RocketMQ，且引入 Canal 会增加额外的架构复杂度和运维成本（Binlog 解析、HA 部署），我们优先选择了基于 MQ 的延迟双删 \+ 兜底重试的方案，它在当时的场景下是成本和效果的一个平衡点。

### **5\. 项目一：仿小红书（CompletableFuture 并发优化）**

场景描述：  
在“仿小红书”的“笔记详情页”，是一个典型的聚合场景。当用户点开一篇笔记时，后端接口需要同时调用多个下游微服务：

1. 调用**用户服务**（获取作者的头像、昵称）。  
2. 调用**评论服务**（获取笔记的评论列表）。  
3. 调用**互动服务**（获取当前登录用户是否点赞、是否收藏了这篇笔记）。  
4. （可能还）调用**笔记服务**（获取笔记内容本身）。

**优化前（串行）**：如果串行调用，总耗时 T \= T(用户) \+ T(评论) \+ T(互动)。即使每个 Feign 调用平均 40ms，总耗时也会轻松超过 120ms，就像简历里的 134ms。

优化后（并行编排）：  
我使用了 CompletableFuture 来将这些串行调用改为并行执行：

1. 我会为每一个 Feign 调用创建一个 CompletableFuture 任务，例如：  
   * CompletableFuture\<UserDTO\> userFuture \= CompletableFuture.supplyAsync(() \-\> userService.getUserInfo(authorId), customThreadPool);  
   * CompletableFuture\<List\<CommentDTO\>\> commentFuture \= CompletableFuture.supplyAsync(() \-\> commentService.getComments(noteId), customThreadPool);  
   * CompletableFuture\<InteractDTO\> interactFuture \= CompletableFuture.supplyAsync(() \-\> interactService.getInteractStatus(noteId, userId), customThreadPool);  
2. 然后，我使用 CompletableFuture.allOf(userFuture, commentFuture, interactFuture) 来等待**所有**异步任务都执行完毕。  
3. 最后，调用 .join() 方法（或 .get()）从各个 Future 中获取结果，将它们组装成一个最终的 VO（View Object），返回给前端。

由于这些任务是并行执行的，总耗时 T 约等于**耗时最长**的那个 Feign 调用（max(T(用户), T(评论), T(互动))），再加上一点组装的开销。因此，接口响应时间从 134ms 显著降低到了 80ms。

关于线程池：  
我没有使用 CompletableFuture 默认的 ForkJoinPool.commonPool()。

* **风险**：commonPool 是 JVM 全局共享的，核心线程数默认是 CPU 核心数-1。在 Spring Boot Web 应用中，如果所有 I/O 密集型任务（如 Feign、MySQL、Redis 调用）都挤占 commonPool，很容易导致池中所有线程都被阻塞在 I/O 等待上，造成线程池“饿死”，其他依赖 commonPool 的任务（如 parallelStream）将无法执行。  
* **我的处理**：正如简历中提到的“自研动态线程池”（虽然写在了发短信那里，但原理是通用的），我会**自定义一个专用的线程池**（ThreadPoolExecutor）来执行这些 Feign 调用。  
  * 这个线程池会针对 I/O 密集型场景进行配置：corePoolSize 和 maximumPoolSize 会设置得相对较大（例如 CPU 核心数的 2-4 倍），并使用合理的队列（如 LinkedBlockingQueue）和拒绝策略。  
  * 然后，我将这个 customThreadPool 作为参数传给 supplyAsync()，实现业务线程池和 commonPool 的隔离，防止 I/O 任务饿死 CPU 任务。

### **6\. 项目二：MyDB（2PL 与 MVCC 的共存）**

面试官您看得非常仔细。在我的 "MyDB" 项目中（以及在真实的 InnoDB 中），2PL（两段锁协议）和 MVCC 确实是**同时存在、相辅相成**的，它们服务于不同类型的读操作，共同保障了隔离级别。

* **MVCC (多版本并发控制)**：  
  * **服务于**：**快照读 (Snapshot Read)**。  
  * **例子**：即最普通的 SELECT ... 语句。  
  * **作用**：在“可重复读”（RR）级别下，快照读通过 Read View 和 Undo Log 版本链，去读取事务启动时的数据快照。  
  * **优点**：**读不加锁**，实现了“读写不阻塞”。  
* **2PL (两段锁协议)**：  
  * **服务于**：**当前读 (Current Read)**。  
  * **例子**：  
    * SELECT ... LOCK IN SHARE MODE （加 S 锁）  
    * SELECT ... FOR UPDATE （加 X 锁）  
    * INSERT / UPDATE / DELETE (DML 操作本质上也是当前读，因为它们必须读取并锁定最新版本的数据来进行修改)。  
  * **作用**：保证在“当前读”和 DML 操作时，读取到的是数据库的**最新版本**，并且锁定该数据，防止其他事务并发修改。

如何共存 (How)：  
在我的 "MyDB" 中，当系统（在 RR 级别）执行：

1. **快照读 (SELECT)**：它会走 MVCC 逻辑。创建或复用 Read View，去版本链里查找可见的版本，**不加任何锁**。  
2. **当前读 (DML 或 SELECT ... FOR UPDATE)**：它会走 2PL 逻辑。**忽略 MVCC**，直接读取数据的最新版本，并在读取时，必须获取相应的锁（S 锁或 X 锁）。如果获取不到锁，事务就会阻塞，等待锁释放。

总结：  
MVCC 是为了让“读”（快照读）操作不阻塞“写”操作。  
2PL 则是为了让“写”（DML/当前读）操作会阻塞“写”操作（以及“当前读”操作）。  
在 InnoDB (以及我的 "MyDB" 所模仿的) 中，**“可重复读”隔离级别 \= MVCC（用于快照读）+ 2PL（用于当前读）**。

* **死锁检测**：在 2PL 的实现中，我（在项目中）也实现了死锁检测。这是通过构建一个“事务等待图”（Wait-for-Graph）来实现的。当事务 T1 申请锁（被 T2 持有）而进入等待时，系统会检查 T2 是否也在等待 T1 持有的锁。如果检测到图（T1 \-\> T2 \-\> T1）中存在环路，就判定发生死锁。此时，系统会选择一个事务（例如 Undo Log 最小的）作为牺牲品，将其回滚，以打破死锁。

### **7\. 实习经历（TCP \-\> HTTP）**

为什么 HTTP 是“高可用”：  
您说的很对，从协议本身看，TCP 是可靠协议。我简历中提到的“高可用”其实是指整个系统架构的健壮性（Robustness）和可运维性（Maintainability）。

* **原生 TCP 的痛点**：  
  1. **协议私有**：我们原生的 TCP 协议是自定义的，涉及复杂的数据帧、心跳、粘包/半包处理。这对客户端（Android）开发和后期维护非常不友好。  
  2. **连接脆弱**：在 Android 这种移动弱网环境下，网络切换（4G/Wi-Fi）、进电梯等会导致 TCP 长连接频繁断开。一旦断开，就需要非常复杂的客户端重连和状态同步逻辑。  
  3. **运维黑盒**：私有 TCP 协议在通过防火墙、Nginx 等中间件时配置复杂，且难以监控、调试和水平扩展。  
* **HTTP 的优势（为什么重构）**：  
  1. **标准与生态**：HTTP 是公认的标准。客户端（OkHttp）和服务端（Spring MVC）都有极其成熟的库，自带连接池、超时、重试等机制。  
  2. **适应弱网**：HTTP（短连接或 Keep-Alive）天然是“请求-响应”模式。即使这次请求因为网络抖动失败了，客户端只需要发起一次简单的**重试**即可，无需维护复杂的连接状态。  
  3. **易于扩展与监控**：HTTP 接口可以无缝接入 Nginx、API 网关（如 Gateway），享受成熟的负载均衡、限流、熔断、HTTPS 加密、ELK 日志监控等全套服务。这使得整个系统的**可用性**、**可观测性**和**弹性**大大提高。

HTTP 断点续传的实现：  
我们引入的断点续传机制，主要是利用了 HTTP 1.1 的 Range 和 Content-Range 头部（主要用于大文件，如通话录音的上传）：

* **场景**：Android 端需要上传一个 10MB 的录音文件。  
* **流程**：  
  1. **分片上传**：客户端（Android）不会一次性 POST 整个 10MB 文件，而是将其分片（例如，每片 1MB）。  
  2. **使用 Content-Range 头部**：在上传每个分片时，客户端会使用 Content-Range 头部来告诉服务器这是文件的哪一部分。  
     * 第一次上传（第 0-999,999 字节）：Content-Range: bytes 0-999999/10000000  
     * 第二次上传（第 1,000,000-1,999,999 字节）：Content-Range: bytes 1000000-1999999/10000000  
  3. **中断与恢复**：  
     * 客户端在本地会持久化记录“已成功上传到第几字节”（例如，传完第 1 片后，记录 1,000,000）。  
     * 如果此时 App 崩溃或网络中断。  
     * 当 App 重启或网络恢复后，它会从本地记录读取进度，然后从第 1,000,001 字节（即第 2 片）开始，继续使用 Content-Range 头部上传。  
  4. **服务端**：服务器（例如我们后端的 Minio 或自研的接收接口）会根据 Content-Range 头部，将收到的分片数据追加到正确的文件偏移量上。

通过这套机制，我们替换了原生的 TCP 传输，使得大文件在弱网环境下的上传成功率大大提高，显著降低了数据丢包率。
