## MyDB

我先说一下这个项目的数据分为三个层次，一个是数据页，一个是数据项，一个数据页管理多个数据项，任何形式的数据进行存储时都会包装成一个数据项，因为数据项有一个 long 类型的 uid，uid 的前32位保存的是数据页的位置，后32位保存自身在数据页的偏移，还有第三个层次是记录

记录是由三部分组成
第一个是创建该条记录（版本）的事务编号、
第二个则是删除该条记录（版本）的事务编号。
DATA 就是这条记录持有的数据

在这个项目中，默认是可重复读
在执行每条语句时都会携带一个事务 id 
在进行查询语句时，先根据查询条件，查询所有符合条件的记录，再根据事务 id 进行筛选

1. **判断是否是当前事务自己插入的未删除数据**：
    
    - 如果数据的创建者是当前事务（`xmin == xid`），并且尚未被标记删除（`xmax == 0`），则当前事务可以看到自己插入的数据，返回`true`。
2. **判断是否是其他已提交事务创建且未被当前事务删除的数据**：
    
    - 首先检查数据的创建者（`xmin`）是否已提交（`tm.isCommitted(xmin)`），并且创建事务的 ID 早于当前事务（`xmin < xid`），同时创建事务不在当前事务的快照中（`!t.isInSnapshot(xmin)`）。这意味着创建操作在当前事务开始前已完成。
    - 在满足上述条件的基础上：
        - 如果数据尚未被标记删除（`xmax == 0`），则当前事务可以看到该数据，返回`true`。
        - 如果数据已被标记删除（`xmax != 0`），需要进一步检查删除操作是否由当前事务执行：
            - 若删除操作不是由当前事务执行（`xmax != xid`），则检查删除事务的状态：
                - 如果删除事务未提交（`!tm.isCommitted(xmax)`），或删除事务的 ID 晚于当前事务（`xmax > xid`），或删除事务在当前事务的快照中（`t.isInSnapshot(xmax)`），说明删除操作对当前事务不可见，返回`true`。



## MySQL

MySQL 实现时基于 Undo Log 和 Read View

每次修改数据前，先将记录拷贝到 Undo Log，并且每条记录会包含三个隐藏列，DB_TRX_ID 用来记录修改该行的事务 ID，DB_ROLL_PTR 用来指向 Undo Log 中的前一个版本，DB_ROW_ID 用来唯一标识该行数据（仅无主键时生成）
每次读取数据时，都会生成一个 ReadView，其中记录了当前活跃事务的 ID 集合、最小事务 ID、最大事务 ID 等信息，通过与 DB_TRX_ID 进行对比，判断当前事务是否可以看到该数据版本

# 如何实现事务的原子性

原子性是指在一个事务中，多个操作要么都成功，要么都失败。

首先使用 ReentrantLock 确保事务的有序性，

一行记录是由三部分组成，一部分是创建该记录时的 id， 一部分是存储数据，一部分是XMAX 则是删除该条记录（版本）的事务编号

因此在进行删除操作时，会先保存原有的数据，然后改变其删除该条记录（版本）的事务编号，最高确认更改，生成日志

在更新操作时，先解析 Where 字段分析出记录的唯一标识 uid，然后根据这个 uid，将所有可见的记录进行删除操作，最后生成一个新的记录插入数据库，最后生成日志

在数据库根据日志文件重写数据时，会判断此事务是否提交，如果没有提交就不会写入到数据库中

# 项目中提到了死锁处理，你能说说在这个项目里是如何检测和处理死锁的吗

1. **初始化标记**：

    - 为每个事务分配一个 “时间戳”（`xidStamp`），用于标记 DFS 的访问状态。
    - `stamp` 是全局递增的时间戳，用于区分不同的 DFS 路径。

2. **遍历所有事务**：

    - 对每个事务（XID），如果它还没有被标记过，则启动一次 DFS。

3. **深度优先搜索（DFS）**：

    - **标记当前事务**：设置将当前事务标记为 “正在访问”（时间戳设为当前 `stamp`）。
    - **查找等待关系**：检查当前事务正在等待的资源（`waitU.get(xid)`），并找到持有该资源的事务（`u2x.get(uid)`）。
    - **递归检查**：递归访问持有资源的事务，看是否最终会回到当前事务（形成循环）。
        - 如果遇到一个已被标记为当前 `stamp` 的事务，说明发现循环，返回 `true`（死锁）。
        - 如果遇到一个已被标记为其他 `stamp` 的事务，说明该路径无循环，跳过。


# `DataManager` 中的 `insert` 和 `read` 方法是核心操作，你能分析一下它们的实现逻辑吗

## insert

会先查找一个有足够空闲空间的数据页，然后将这个数据也从数据页列表中移除，确保只有一个线程操作这个数据页，插入完成后，重新计算这个数据页的空闲空间，插入到数据页列表中

## read

read 查询语句有两个核心参数，一个是当前的事务 id，一个查询条件，
先根据查询条件找到对应的表，然后根据 B+ 树索引找到对应记录的 uid，这个 uid 是 64 位，前 32 位是数据页的位置，后 32 位是记录在数据页的位置
然后再根据当前事务的 id 判断记录是否可见

#  在 `BPlusTree` 类中，`searchRange` 方法用于在 B+ 树中搜索指定范围的键值，能详细解释一下这个方法的实现过程吗？

1. **获取根节点的 `uid`**：调用 `rootUid()` 方法获取 B+ 树的根节点的 `uid`。
2. **找到包含 `leftKey` 的叶子节点**：调用 `searchLeaf(rootUid, leftKey)` 方法从根节点开始递归搜索，直到找到包含 `leftKey` 的叶子节点。
3. **初始化结果列表**：创建一个空的 `ArrayList` 用于存储找到的 `uid`。
4. **遍历叶子节点**：
    - 加载当前叶子节点。
    - 调用 `leaf.leafSearchRange(leftKey, rightKey)` 方法在当前叶子节点中搜索指定范围的键值，并返回结果。
    - 释放当前叶子节点的资源。
    - 将找到的 `uid` 添加到结果列表中。
    - 判断是否还有兄弟节点，如果有则更新 `leafUid` 为兄弟节点的 `uid`，继续循环；如果没有则跳出循环。
5. **返回结果列表**：返回包含所有找到的 `uid` 的列表。



# `BPlusTreeTest` 中测试了 B+ 树的插入和搜索功能，能说说 B+ 树在数据库中的作用以及它的优势吗

## 作用

- **索引结构**：B+ 树在数据库中主要用作索引结构，用于加速数据的查找、插入、删除和更新操作。通过在索引中存储键值和对应的记录位置，可以快速定位到满足查询条件的记录，避免了全表扫描，从而提高了数据库的查询效率。
- **范围查询**：B+ 树的叶子节点按顺序连接成一个链表，因此非常适合进行范围查询。可以通过遍历叶子节点链表，快速找到指定范围内的所有记录。
- **数据排序**：B+ 树的键值是有序存储的，因此可以用于对数据进行排序。在查询时，可以直接按照键值的顺序返回结果，无需额外的排序操作。

## 优势

- **高度平衡**：B+ 树是一种高度平衡的树结构，所有叶子节点都在同一层，因此可以保证查询的时间复杂度为 O(logn)，其中 n 是树中节点的数量。这使得 B+ 树在处理大量数据时具有较好的性能。
- **磁盘友好**：B+ 树的节点大小通常与磁盘块大小相匹配，因此可以减少磁盘 I/O 操作。在进行查询时，只需要读取少量的磁盘块就可以找到所需的记录，从而提高了磁盘 I/O 效率。
- **范围查询高效**：由于 B+ 树的叶子节点按顺序连接成一个链表，因此可以快速进行范围查询。只需要从链表的起始位置开始遍历，直到找到满足条件的所有记录，避免了多次随机访问磁盘。
- **插入和删除操作稳定**：B+ 树在插入和删除操作时，通过分裂和合并节点来保持树的平衡，因此插入和删除操作的时间复杂度也是 O(logn)，并且不会影响树的整体性能。
