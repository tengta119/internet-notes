# 日志系统

## **traceId** 

是一个请求的唯一标识，通常是由IP地址、时间戳、进程号（5位）、自增序列号，也有其他的实现方式，主要是为了保证每个请求的 **traceId** 的唯一性。

```bash
# traceId 示例
00000000.1686895888832.745811000
00000000.1686895888838.745811001
75e0cde204164cda98b0cca40b2999da.1.16868958889180000
```



* 为什么需要 **traceId：**

当你的系统是分布式或者微服务时，一个球友可能会穿过多个服务，每个服务可能都会生成一些日志，但由于系统是微服务/分布式的，会运行在不同的物理机器上，如果没有一个统一的标识符来链接这些日志，就很难理解一个请求的完整过程。

traceid 就是这样一个标识符，它在请求进入系统时生成，然后沿着请求的执行路径传递给所有参与处理该请求的服务。这些服务在生成日志时，会把traceid包含在日志中。这样，通过搜索同一traceid的所有日志，就可以追踪到整个请求的执行过程。



## MDC 映射诊断上下文

MDC 基于 ThreadLocal 实现，实现在线程中全局唯一性

MDC 是日志追踪的“胶水”，通过线程上下文自动传递关键信息，它常与 traceId 结合，成为全链路诊断的核心工具。



## AOP

1）横切关注点，它是一个抽象的概念，没有具体的代码表现形式。它是在分析系统需求时总结出来的一类共性需求。

2）切面（Aspect），对横切关注点进行封装的类，每个关注点体现为一个通知方法；通常使用 [@Aspect ](https://www.yuque.com/Aspect) 注解来定义切面。 

3）通知（Advice），切面必须要完成的各个具体工作，比如我们的日志切面需要记录接口调用前后的时长，就需要在调用接口前后记录时间，再取差值。通知的方式有五种：

●@Before：通知方法会在目标方法调用之前执行
●@After：通知方法会在目标方法调用后执行
●@AfterReturning：通知方法会在目标方法返回后执行
●@AfterThrowing：通知方法会在目标方法抛出异常后执行
●@Around：把整个目标方法包裹起来，在被调用前和调用之后分别执行通知方法

4）连接点（JoinPoint），通知应用的时机，比如接口方法被调用时就是日志切面的连接点。

5）切点（Pointcut），通知功能被应用的范围，比如本篇日志切面的应用范围是所有 controller 的接口。通常使用 [@Pointcut ](https://www.yuque.com/Pointcut) 注解来定义切点表达式。

# 请求参数解析



## HttpServletRequestWrapper

当我们从 `HttpServletRequest` 中的 `InputStream` 获取参数时只能获取一次，`InputStream` 是一种流，从技术角度来看，当我们从输入流中读取数据时，读取的位置（通常称为“游标”或“指针”）会向前移动。当读完所有的数据后，游标就移到了流的末尾，所以不能再读取更多的数据了。

`HttpServletRequestWrapper`这个类的主要功能是包装 `HttpServletRequest` 对象，以便可以多次读取请求体中的内容

![image-20250327171322155](D:/typoraImage/image-20250327171322155.png)

## GET请求

### RequestParam 

用于从请求中获取参数。它将请求参数绑定到你的控制器方法的参数上

### PathVariable

是 Spring MVC 中的一个注解，可以将 URL 中的占位符参数绑定到控制器处理方法的参数上



## POST

 `HttpServletRequest.getParameter(String name) ` 方法可以用于获取 HTTP 请求中的参数，但是，这个方法通常用于获取 GET 请求中的参数或者 `application/x-www-form-urlencoded` 编码的 POST 请求参数。

如果 POST 请求中的参数是 JSON 格式的，那么这些参数通常位于请求的 body 中，getParameter()方法无法直接获取这些参数

### RequestBody 

RequestBody注解用于将请求体绑定到一个方法参数上。通常用于处理 POST、PUT 等方法的请求，这些请求通常会在请求体中发送数据。在方法参数上添加RequestBody注解，Spring 会使用一个 HttpMessageConverter 将请求体转换为对应的 Java 对象

### **MultipartFile**

MultipartFile 是 Spring 中处理文件上传的一个接口。当我们通过 `multipart/form-data` 形式的 HTTP POST 请求上传文件时，Spring MVC 会将上传的文件包装为 MultipartFile 对象。我们可以通过 RequestParam注解的形式直接获取一个 MultipartFile 对象

# 技术派Redis的缓存示例

在 Redis 操作的上下文中，使用回调接口（如`execute(RedisCallback<T> action)`）和直接操作命令各有特点，下面为你详细分析两者的区别：

## 回调接口和直接操作命令的区别

### 1. 灵活性

- 回调接口
  - 回调接口提供了极高的灵活性。通过它你可以自定义 Redis 操作逻辑，不仅可以执行单个命令，还能组合多个命令，实现复杂的操作序列。例如，你可以在回调中执行一个事务，包含多个不同类型的命令，并且可以根据执行结果进行条件判断和处理。
  - 以下是一个使用回调接口执行 Redis 事务的伪代码示例：

```java
redisTemplate.execute((RedisCallback<Object>) connection -> {
    connection.multi(); // 开启事务
    connection.set("key1".getBytes(), "value1".getBytes());
    connection.get("key2".getBytes());
    List<Object> results = connection.exec(); // 执行事务
    return results;
});
```



- 直接操作命令
  - 直接操作命令通常只能执行单个预定义的操作，灵活性相对较差。它更适合执行简单、独立的 Redis 命令，例如设置一个键值对或者获取一个键的值。像`redisTemplate.opsForValue().set("key", "value");` 只能执行一个单独的`SET`命令。

### 2. 性能

- 回调接口
  - 当需要执行多个命令时，使用回调接口可以减少与 Redis 服务器的交互次数，从而提高性能。因为在回调中可以将多个命令一次性发送给 Redis 服务器执行，避免了多次网络往返的开销。
  - 例如，你需要批量设置多个键值对，使用回调接口可以将这些`SET`命令一次性发送给服务器：

```java
redisTemplate.execute((RedisCallback<Object>) connection -> {
    for (Map.Entry<String, String> entry : keyValueMap.entrySet()) {
        connection.set(entry.getKey().getBytes(), entry.getValue().getBytes());
    }
    return null;
});
```



- 直接操作命令
  - 每次执行一个命令都需要与 Redis 服务器进行一次网络交互，当需要执行多个命令时，会增加网络延迟，性能相对较低。例如，依次执行多个`SET`命令：

```java
for (Map.Entry<String, String> entry : keyValueMap.entrySet()) {
    redisTemplate.opsForValue().set(entry.getKey(), entry.getValue());
}
```

### 3. 代码复杂度

- 回调接口
  - 回调接口的代码复杂度相对较高。因为需要处理底层的连接和命令执行，并且要考虑异常处理等情况。例如，在回调中需要手动处理连接的关闭和异常捕获，以确保资源的正确释放。

```java
redisTemplate.execute((RedisCallback<Object>) connection -> {
    try {
        // 执行命令
        connection.set("key".getBytes(), "value".getBytes());
        return null;
    } catch (Exception e) {
        // 异常处理
        e.printStackTrace();
        return null;
    }
});
```



- 直接操作命令
  - 直接操作命令的代码更加简洁易懂，适合初学者或者处理简单的业务场景。例如，设置一个键值对只需要一行代码：`redisTemplate.opsForValue().set("key", "value");`

### 4. 错误处理

- 回调接口
  - 在回调接口中，你可以对整个操作序列进行统一的错误处理。可以捕获和处理回调中所有命令执行过程中可能出现的异常，保证操作的一致性和可靠性。
- 直接操作命令
  - 直接操作命令的错误处理相对分散，每个命令的执行都需要单独进行错误处理。例如，在执行多个命令时，需要为每个命令的调用添加异常捕获代码。



综上所述，如果你需要执行复杂的操作序列、追求高性能，并且能够处理较高的代码复杂度，那么使用回调接口是更好的选择；如果你只是执行简单的单个命令，追求代码的简洁性和易读性，那么直接操作命令会更合适。
