            .baseUrl(baseUrl)  
            .client(okHttpClient)  
            .addCallAdapterFactory(RxJava2CallAdapterFactory.create())  
            .addConverterFactory(JacksonConverterFactory.create())  
            .build().create(IOpenAiApiProxy.class);  
}

# 《AI MCP Gateway》第2-3节：MCP通信协议(json-rpc2)

![](attachments/Pasted%20image%2020260304173108.png)



**1. 核心角色**

在 MCP 架构中，主要有三个参与者：

- **AI 宿主 (MCP Host)**：用户使用的 AI 客户端，如 Claude Desktop、Cursor IDE。它负责**发起**请求。
    
- **MCP 客户端 (MCP Client)**：运行在 AI 宿主内部，充当“翻译官”。它负责连接各个 MCP Server。
    
- **MCP 服务端 (MCP Server)**：提供具体功能的后端程序（例如操作本地文件、查询数据库）。它负责**执行**任务。
    

---

 **2. 调用流程：从指令到执行**

当你在 AI 对话框中输入“读取我桌面上的 `notes.txt`”时，发生的调用过程如下：

 第一步：发现与握手 (Discovery)

当 AI 启动时，MCP Client 会扫描配置文件（如 `claude_desktop_config.json`），连接到已注册的 MCP Server。

- Client 向 Server 发送 `tools/list` 请求。
    
- Server 返回自己拥有的“技能清单”（例如：`read_file`, `write_file`）。
    
- **结果**：AI 模型现在知道自己有哪些“手脚”可以动了。
    

第二步：意图识别 (Inference)

你发送指令：“读取 `notes.txt`”。

- AI 宿主将你的话发给模型（LLM）。
    
- 模型发现自己无法直接读取文件，但看到清单里有 `read_file` 工具。
    
- 模型回复一个结构化的**工具调用请求 (Tool Call)**，包含参数：`{"tool": "read_file", "path": "~/Desktop/notes.txt"}`。
    

第三步：协议传输 (Communication)

- MCP Client 接收到模型的意图，将其封装成 **JSON-RPC 2.0** 格式的消息。
    
- 通过传输层（通常是 **stdio** 本地管道或 **HTTP+SSE** 远程连接）发送给 MCP Server。
    

 第四步：本地执行 (Execution)

- MCP Server（比如一个 Python 或 Node.js 脚本）接收到 JSON 指令。
    
- 它在本地操作系统上执行真实的读文件操作。
    
- 执行完成后，将文件内容包装成 JSON 响应回传给 MCP Client。
    

第五步：结果反馈 (Final Output)

- AI 宿主将文件内容喂回给模型。
    
- 模型处理这些内容，最终用自然语言告诉你：“我已经读到了，文件内容是...”
    

---

**3. 两种主要的传输方式**

AI 调用 MCP 的底层“连接线”通常有两种：

|**方式**|**场景**|**特点**|
|---|---|---|
|**stdio (标准输入输出)**|本地工具（如 Claude Desktop 访问本地文件）|速度极快，进程间通信，最常用。|
|**SSE (HTTP 扩展)**|远程服务（如访问部署在云端的数据库）|支持跨机器通信，基于 Web 标准。|

 **1. 协议层：数据交换的标准**

- **JSON-RPC 2.0**:
    
    - **本质**：轻量级远程过程调用协议，规定了 JSON 传输的固定格式（`method`, `params`, `id`）。
        
    - **特点**：无状态、支持批量调用、不限制传输层（HTTP/TCP/WebSocket 均可）。
        
- **SSE (Server-Sent Events)**:
    
    - **本质**：基于 HTTP 的单向推送协议（Server -> Client）。
        
    - **优势**：比 WebSocket 轻量，浏览器原生支持自动重连，非常适合 AI 流式输出和通知推送。
        

---

**2. 框架层：Java 响应式编程 (Project Reactor)**

- **核心逻辑**：解决“一个请求一个线程”的阻塞问题，通过少量线程处理高并发 IO。
    
- **核心组件**：
    
    - **Mono**: 异步序列，包含 0 或 1 个元素。
        
    - **Flux**: 异步序列，包含 0 到 N 个元素。
        
    - **背压 (Backpressure)**：下游消费者可以告诉上游生产者“慢一点发”，防止系统被冲垮。
        

---

**3. 实现层：如何构建实时推送系统**

- **Sinks.Many (消息中转站)**:
    
    - **作用**：在非响应式代码（如普通方法、定时任务）与响应式流（Flux）之间建立桥梁。
        
    - **模式**：`multicast()`（广播给所有用户）或 `unicast()`（发给单个用户）。
        
-  **ServerSentEvent\<T> (快递包装盒)**:
    
    - **组成**：包含 `data`（核心数据）、`id`（重连依据）、`event`（事件分类）、`retry`（重连频率）。
        
    - **意义**：相比直接返回 `String`，它提供了更强的元数据控制，方便前端根据不同 `event` 执行不同逻辑。
        

---

**技术链路总结图**

|**组件**|**角色**|**形象比喻**|
|---|---|---|
|**业务逻辑**|生产者|产生零散消息的工厂|
|**Sinks.Many**|缓冲区|收集零件并排队的仓库|
|**Flux**|传送带|持续不断运输数据的流水线|
|**ServerSentEvent**|包装标准|贴有面单（ID/类型）的标准快递盒|
|**HTTP (SSE)**|运输管道|连接服务器与浏览器的专属隧道|

## 例子

**1. 场景模拟**

假设我们要实现一个**“全局系统通知”**：

1. 任何一个管理员在后台发布公告，所有在线用户都能立刻收到。
    
2. 每一个公告都会被包装成 `ServerSentEvent` 发送。
    

---

**2. 完整示例代码**

**第一步：创建一个单例的“消息中转站”**

我们需要一个中心化的 `Sink` 来收集消息。

```java
@Service
public class NotificationService {

    // 1. 定义这个“桶” (Sink)
    // many(): 发送多个元素
    // multicast(): 广播给所有订阅者
    // onBackpressureBuffer(): 如果发太快，先存在内存里
    private final Sinks.Many<ServerSentEvent<String>> sink = 
            Sinks.many().multicast().onBackpressureBuffer();

    // 2. 业务方法：用来往“桶”里丢消息
    public void publishNotification(String adminName, String content) {
        ServerSentEvent<String> sse = ServerSentEvent.<String>builder()
                .id(UUID.randomUUID().toString())
                .event("sys-note") // 事件类型
                .data(adminName + " 发布了公告: " + content)
                .build();
        
        // 关键：把消息推入 Sink
        sink.tryEmitNext(sse);
    }

    // 3. 暴露流：给 Controller 订阅
    public Flux<ServerSentEvent<String>> getNotificationStream() {
        return sink.asFlux();
    }
}
```

**第二步：创建控制器（HTTP 长连接出口）**

这里就是“顺着 HTTP 长连接排队推给前端”的地方。

```java
@RestController
public class NotificationController {

    private final NotificationService notificationService;

    public NotificationController(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    // 设置 produces 为 TEXT_EVENT_STREAM_VALUE，这就是告诉浏览器：我要开始推流了
    @GetMapping(value = "/notifications/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> stream() {
        return notificationService.getNotificationStream();
    }
}
```

**第三步：模拟业务触发**

模拟一个普通的 REST 接口，触发消息推送。

```java
@PostMapping("/admin/send")
public String send(@RequestParam String user, @RequestParam String msg) {
    notificationService.publishNotification(user, msg);
    return "已加入推送队列";
}
```

---

**3. 如何理解“排队”推送？**

4. **收集（Sinks.Many）**：当你调用 `tryEmitNext` 时，消息就像进入了一个 **FIFO（先进先出）队列**。
    
5. **转换（asFlux）**：`Sink` 把这些离散的调用转化成了一个持续不断的“流”（Flux）。
    
6. **排队（Backpressure）**：如果前端网络慢（比如手机进隧道了），`onBackpressureBuffer()` 会让这些消息在内存里暂时排队，等网络恢复了再按顺序推出去。
    
7. **推送（SSE）**：由于 HTTP 连接一直没断开，每当 `Sink` 里多了一条数据，WebFlux 就会自动把这块 JSON 按照 SSE 的格式封装，发给浏览器。
    

**8. 为什么不直接用 List？**

- **List 是静态的**：你返回一个 List，连接就结束了。
    
- **Flux + Sink 是动态的**：连接始终打开，只要 `Sink` 不关闭，前端就能一直收到新消息。
    

# 《AI MCP Gateway》第3-4节：会话消息结构设计

```java
@Slf4j  
public final class McpSchemaVO {  
  
    private static final TypeReference<HashMap<String, Object>> MAP_TYPE_REF = new TypeReference<>() {  
    };  
  
    private static final ObjectMapper objectMapper = new ObjectMapper();  
  
    public static JSONRPCMessage deserializeJsonRpcMessage(String jsonText)  
            throws IOException {  
  
        log.debug("Received JSON message: {}", jsonText);  
  
        var map = objectMapper.readValue(jsonText, MAP_TYPE_REF);  
  
        if (map.containsKey("method") && map.containsKey("id")) {  
            return objectMapper.convertValue(map, JSONRPCRequest.class);  
        } else if (map.containsKey("result") || map.containsKey("error")) {  
            return objectMapper.convertValue(map, JSONRPCResponse.class);  
        }  
  
        throw new IllegalArgumentException("Cannot deserialize JSONRPCMessage: " + jsonText);  
    }  
  
    /**  
     * JSON-RPC 2.0 Message Types     
    */    
    public sealed interface JSONRPCMessage permits JSONRPCRequest, JSONRPCResponse {  
  
        String jsonrpc();  
  
    }  
  
    /**  
     * 请求对象  
     *  
     * @param jsonrpc 协议版本 2.0  
     * @param method  请求方法；initialize、tools/list、tools/call、resources/list  
     * @param id      请求ID  
     * @param params  请求参数  
     */  
    @JsonInclude(JsonInclude.Include.NON_ABSENT)  
    @JsonIgnoreProperties(ignoreUnknown = true)  
    public record JSONRPCRequest(@JsonProperty("jsonrpc") String jsonrpc,  
                                 @JsonProperty("method") String method,  
                                 @JsonProperty("id") Object id,  
                                 @JsonProperty("params") Object params  
    ) implements JSONRPCMessage {  
    }  
    /**  
     * 响应对象  
     *  
     * @param jsonrpc 协议版本 2.0  
     * @param id      请求ID  
     * @param result  响应结果  
     * @param error   异常结果  
     */  
    @JsonInclude(JsonInclude.Include.NON_ABSENT)  
    @JsonIgnoreProperties(ignoreUnknown = true)  
    public record JSONRPCResponse(  
            @JsonProperty("jsonrpc") String jsonrpc,  
            @JsonProperty("id") Object id,  
            @JsonProperty("result") Object result,  
            @JsonProperty("error") JSONRPCError error  
    ) implements JSONRPCMessage {  
        @JsonInclude(JsonInclude.Include.NON_ABSENT)  
        @JsonIgnoreProperties(ignoreUnknown = true)  
        public record JSONRPCError(  
                @JsonProperty("code") int code,  
                @JsonProperty("message") String message,  
                @JsonProperty("data") Object data) {  
        }    }  
  
}
```
